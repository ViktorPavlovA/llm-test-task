# Backend тестового задания на позицию **AI/LLM-разработчик**

Сервис собирает черновик карточки товара для B2B-каталога контрольно-измерительных приборов. На вход — JSON или веб-форма. На выход — SEO-заголовок, описание 800–1200 символов, характеристики, поисковые запросы и коммерческий блок.

Локальная модель поднимается сервисом `service_llm_local` (OpenAI-совместимый API на порту `8686`). Этот сервис собирает карточку через LangGraph: если во входе не хватает характеристик, research-агент ищет паспорт в интернете (`search_web`, `fetch_page`), затем writer собирает SEO-текст.

## Запуск

Проще всего поднять оба сервиса из корня репозитория:

```bash
cd ..
docker compose up --build
```

Удобная форма для проверки: http://127.0.0.1:8000  

Документация API: http://127.0.0.1:8000/docs


Ключ и URL модели читаются из `.env`. Используется llama.cpp — локальная модель, поэтому там **вымышленный** `MODEL_API_KEY`.


### Структура параметров .env

```
MODEL_API=http://127.0.0.1:8686/v1  # изменить если используете api
MODEL_API_KEY=local # изменить если используете api
LLM_MODEL=local-llm  # изменить если используете api
LLM_SEARCH_INTERNET=false # использовать инстурумент поиска в интернете
SEARCH_MAX_RESULTS=5 # количество попыток поиска
SEARCH_CONTEXT_CHARS=1800 # окно контекста модели
```

Поиск идёт через DuckDuckGo (`ddgs`), отдельный API-ключ не нужен. Контейнеру `description` нужен исходящий интернет. Инструменты `search_web` / `fetch_page` включаются флагом `LLM_SEARCH_INTERNET=true` в `.env`. `SEARCH_CONTEXT_CHARS` ограничивает текст страницы, который агент кладёт в контекст модели (400–8000, по умолчанию 1800, чтобы не вылезать за окно llama.cpp).

## API

### Примеры запросов, консольные:

```bash
curl -sS http://127.0.0.1:8000/api/description \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product_1.json
```

Markdown:

```bash
curl -sS 'http://127.0.0.1:8000/api/description?format=markdown' \
  -H 'Content-Type: application/json' \
  --data-binary @examples/product_1.json
```

### Входной json на вход модели:

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Ответ:

| Поле | Смысл |
| --- | --- |
| `title` | SEO-заголовок ≤ 70 символов |
| `description` | SEO-текст 800–1200 символов |
| `key_specs` | характеристики именно этого прибора: входные specs плюс подтверждённые дополнения |
| `search_queries` | 3–5 запросов |
| `commercial_block` | кому подходит и какие задачи закрывает |
| `data_missing` | что нужно уточнить у поставщика |
| `review_notes` | замечания для менеджера, не для публикации |
| `sources` | URL страниц, если агент искал паспорт в интернете |
| `web_used` | `true`, если узел research запускался |
| `markdown` | та же карточка, сразу для копирования |

### Примеры работы (если не получится запустить)

Вход: `examples/product_1.json`, `examples/product_2.json`.

Готовый результат: `examples/result_1.md`, `examples/result_2.md` и JSON рядом. Сняты с текущего `POST /api/description` на локальной Qwen3.5-4B. В `key_specs` только подтверждённые значения (входные `specs` плюс находки поиска); строк «данных нет» нет, пробелы уходят в `data_missing`.

## Идеи реализации

### Пайплайн — LangGraph: 

`[исходный запрос] → [поиск информации] → [анализ и формализация ответа согласно требованиям] → [выдача выходного json]`.

#### Исходный запрос

Входной JSON проверяется на соответствие формату и валидацию полей. Если всё в порядке, запускается поиск информации.

#### Поиск информации

Запускается только если `LLM_SEARCH_INTERNET=true` и в `data_missing` есть поля, которые надо заполнить. 

Агент на LangChain (`create_react_agent`) получает два инструмента: `search_web` (DuckDuckGo) и `fetch_page` (HTML с проверкой SSRF).

#### Aнализ и формализация ответа согласно требованиям

LLM оставляет все входные `specs` и дополняет их всеми характеристики, которые поиск подтвердил для этого прибора. Пустой каталог КИП в карточку не выводится. Входные `specs` не перезаписываются. 

Данные, которые были найдены поиском, попадают в «Ключевые характеристики», `review_notes` и `sources`.

LLM пишет маркетинговый слой: заголовок, SEO-описание, запросы, коммерческий блок. В системном промпте запрещены новые числа, ГОСТ, сертификаты, цена и гарантия. Ответ запрашивается как JSON.

После генерации сервис:

- обрезает заголовок до 70 символов и описание до 1200;
- если описание короче 800 символов, просит модель расширить текст, затем дописывает только уже известные факты;
- сверяет числа в ответе с входными данными и, если появились лишние, пишет это в `review_notes`.

### Параметры модели

Температура 0.25. Модель — `qwen-3.5` на llama.cpp, шаблон чата из GGUF, thinking выключен для экономии ресурсов.

## Ограничения и компромиссы

- Локальная 4B-модель слабее облачных: тон маркетингового текста плавает, длину 800+ символов иногда приходится добирать пересказом фактов.
- `data_missing` выбирает модель под тип прибора; Python только отсекает уже известные поля.
- Проверка чисел эвристическая: «36 месяцев гарантии» поймается, «тридцать шесть» — нет.
- Поиск зависит от выдачи DuckDuckGo и доступности сайтов; 4B-агент может не вызвать tool или вернуть пустой `found_specs`.
- `fetch_page` не читает PDF и закрывает частные/loopback-адреса.
- Нет CMS, базы, очереди и пакетной обработки 500 синтетических товаров из `test/json_requests`.
- Сервис рассчитан на русский B2B-каталог КИП.
